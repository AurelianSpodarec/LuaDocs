# Working agreements for AI assistants

## Branching — read this first

**All work stays on `dev`. Never merge into `main`.**

- Do not merge, rebase onto, fast-forward, or otherwise integrate anything into
  `main` — not as a "final step", not because a plan or skill says the work is
  finished, not because tests pass.
- Do not run `git merge`, `git rebase main`, `git switch main`, or open a PR
  targeting `main` on your own initiative.
- **Always ask explicitly, and wait for a clear yes, before any merge.** Approval
  for one merge is not approval for the next one.
- Committing work and pushing `dev` to `origin/dev` needs no permission — commit
  and push as a matter of course, without asking. This applies to `dev` only; the
  rules above about `main` are untouched by it.
- Commit only the work you did. Other sessions edit this tree at the same time,
  so stage named paths rather than `git add -A`, and leave changes you did not
  make to whoever made them.

Reading commands are fine (`git log`, `git diff`, `git merge-base` — the last one
only prints a commit hash, it does not merge).

## Commits

Follow `docs/conventions/commit-messages.md`: `type(scope): summary`, imperative,
≤ ~60 characters, no trailing period. **Never** add a `Co-Authored-By` trailer or
any "generated by" tag.

## Where things live

- `CONTEXT.md` — the project glossary. Use its vocabulary (entry, delta, selected
  version, version support) and avoid the terms it lists under _Avoid_.
- `docs/adr/` — decisions. Do not contradict one without saying so.
- `docs/plans/ROADMAP.md` — the ordered slices. Detailed plans are written one
  slice at a time, just before executing.
- `docs/plans/<date>-<slice>.md` — the current slice's implementation plan.
- `/demo` (`src/demo/`) — the internal proving surface. Not reader-facing.

## Rendering decisions get rendered

Per [ADR 0015](docs/adr/0015-rendered-before-ratified.md): a decision that constrains what a
reader **sees** — page anatomy, component props, field lists, layout, label wording — is not
finished until one subject has been rendered under it on `/demo`.

- Pick the subject that exercises the **most rules at once**, not the simplest one.
- The current behaviour renders from the real components in `src/entry/`. The proposal is a
  **copy** under `src/demo/`, never an edit of the shipping component.
- **Write down what the rendering falsified**, and amend the decision before migrating
  content. This is the step that pays; skipping it makes the page decoration.

This exists because ADR 0013 shipped six rules and rendering one entry falsified three of
them. Decisions with nothing to render — licensing, URL maps, sourcing — are out of scope.
