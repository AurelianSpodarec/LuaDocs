Hands control to a coroutine and waits for it to hand control back. The first value returned
is a status: `true` followed by whatever the coroutine passed over, or `false` followed by
the [error object](/docs/standard-library/globals/error#what-an-error-carries) it failed
with. A failure inside the coroutine does not propagate — it arrives here as a value, the
way a protected call reports one.

<RunnableExample code={`local ticket_desk = coroutine.create(function(first_name)\n  local second_name = coroutine.yield("serving " .. first_name)\n  return "served " .. first_name .. " and " .. second_name\nend)\n\nprint(coroutine.resume(ticket_desk, "Ada"))\nprint(coroutine.resume(ticket_desk, "Grace"))\nlocal resumed_again = coroutine.resume(ticket_desk)\nprint(resumed_again)\n-- Expected output:\n-- true\tserving Ada\n-- true\tserved Ada and Grace\n-- false`} />

## Syntax

```lua
coroutine.resume(co [, val1, ···])
```

<Parameters>
  <Param name="co">The coroutine to start or continue.</Param>
  <Param name="val1, ···">Values to hand over. On the first resume of a coroutine they are the arguments to its body; on every later one they are the results of the [`coroutine.yield()`](/docs/standard-library/coroutine/yield) that suspended it.</Param>
</Parameters>

<Returns>
  <Return type="boolean">The status: `true` when the coroutine suspended or finished, `false` when it failed or could not be resumed at all.</Return>
  <Return type="any">On the `true` path, the values the coroutine handed over — those passed to [`coroutine.yield()`](/docs/standard-library/coroutine/yield) if it suspended, or those its body returned if it finished, as many as there were or none at all. On the `false` path, exactly one value — the [error object](/docs/standard-library/globals/error#what-an-error-carries) the failure carried, or a description of why the coroutine could not be resumed — and nothing after it.</Return>
</Returns>

<Errors>

- Raises when `co` is not a coroutine. The argument is checked before anything is resumed, so this failure escapes rather than being reported as a status.
- A coroutine that has already finished does not raise. `false` and a description come back, in the same shape as a failure inside the body.
- A coroutine that is not suspended does not raise either — the one doing the resuming, or one that is itself waiting on a coroutine it resumed. Again `false` and a description come back.

</Errors>

## Description

A resume that actually reaches the coroutine ends in one of three ways, and the status is
the first thing that tells them apart. The coroutine suspended, and `true` comes back with
the values it passed to [`coroutine.yield()`](/docs/standard-library/coroutine/yield). Or its
body returned, and `true` comes back with the values it returned. Or something inside it
raised, and `false` comes back with the error object.

The first two are both `true`, deliberately: from the resuming side a suspension and a
finish look alike, because in both cases the coroutine handed over some values and stopped
running. What separates them is whether the coroutine can be resumed again, and
[`coroutine.status()`](/docs/standard-library/coroutine/status) is what answers that.

A resume that never reaches the coroutine — because it is finished, or because it is not
suspended — takes the same shape as a failure: `false`, then a description of the refusal.
Nothing runs in that case, so a caller that treats every `false` alike is not making a
mistake, only losing the distinction between *the work went wrong* and *there was no work
to do*.

After a failure the coroutine is finished — but its stack is left standing rather than
unwound, so the debug library can still be pointed at it to see where it stopped.

## How control passes between the two sides

A coroutine has two sides: the code that resumes it, and the body it runs. Exactly one of
them is executing at any moment, and the other is stopped mid-expression holding everything
it had — locals, arguments, and a place to carry on from. Control moves between them by hand
and never by itself, which is what makes the order of events here entirely predictable.

`coroutine.resume()` moves control *in*. The values after `co` travel with it: the first
time, they fill in the body's parameters; every time after that, they become the results of
the [`coroutine.yield()`](/docs/standard-library/coroutine/yield) call the body is stopped
in. The body then runs — for one statement or for a million — until it suspends, returns, or
fails.

Control comes back *out* by any of those three routes, and values travel with it in the same
way: whatever the body passed to `coroutine.yield()`, or whatever it returned, appears here
after the status. A suspension can happen at any depth: the body may be six calls deep in
helpers of its own when it yields, and the whole of that stack stays frozen exactly as it
was. Nothing is unwound and nothing is re-run; the next resume continues from inside that
sixth call as though `coroutine.yield()` had simply returned.

Two values, then, cross in opposite directions at each handover, and neither has anything to
do with the other. The arguments to a resume are read by the yield inside the coroutine; the
results of that resume were written by the yield that suspended it.
[`coroutine.wrap()`](/docs/standard-library/coroutine/wrap) performs the same transfer
through a plain function call, dropping the status and letting a failure propagate instead.

## Examples

### Driving a coroutine to the end

<RunnableExample code={`local shopping_list = { "cocoa", "flour", "salt" }\nlocal walk_list = coroutine.create(function()\n  for index = 1, #shopping_list do\n    coroutine.yield(shopping_list[index])\n  end\n  return "nothing left"\nend)\n\nrepeat\n  local completed, item = coroutine.resume(walk_list)\n  print(completed, item)\nuntil coroutine.status(walk_list) == "dead"\n-- Expected output:\n-- true\tcocoa\n-- true\tflour\n-- true\tsalt\n-- true\tnothing left`} />

All four rounds report `true`. Three of them are suspensions and the fourth is the body
returning, and the status carries no trace of the difference — which is why the loop asks the
handle rather than trying to read the answer off the values, where it would have to know
`"nothing left"` when it saw it.

### Handing values in on every resume

<RunnableExample code={`local thermostat = coroutine.create(function(starting_target)\n  local target = starting_target\n  while true do\n    local requested = coroutine.yield(target)\n    target = requested or target\n  end\nend)\n\nprint(select(2, coroutine.resume(thermostat, 19)))\nprint(select(2, coroutine.resume(thermostat, 21)))\nprint(select(2, coroutine.resume(thermostat)))\n-- Expected output:\n-- 19\n-- 21\n-- 21`} />

The first `19` fills in `starting_target`. The `21` after it is read by the `coroutine.yield()`
the body is parked in, and the third resume passes nothing, so that same yield returns no
values and the target stays where it was.

### A failure inside the body

<RunnableExample code={`local double_reading = coroutine.create(function(reading)\n  return reading.value * 2\nend)\n\nlocal completed, reason = coroutine.resume(double_reading, nil)\nprint(completed)\nprint(type(reason))\nprint(coroutine.status(double_reading))\n-- Expected output:\n-- false\n-- string\n-- dead`} />

Indexing a `nil` raises inside the body, and the resuming side learns about it as a status
and an error object rather than by being interrupted. The coroutine is finished either way.

## Gotchas

<Gotcha title="`true` does not mean finished">
The status says the coroutine did not fail; it says nothing about whether there is more to
come. Code that treats `true` as *done* will stop after the first yield with most of the work
still waiting, and code that loops until `false` will loop one round too many and read the
refusal as data. Ask
[`coroutine.status()`](/docs/standard-library/coroutine/status), or have the body return a
value the caller can recognise as its last.
</Gotcha>

<Gotcha title="There is no way to restart one">
A coroutine that has returned or failed stays finished, and resuming it again reports the
refusal rather than running the body a second time. Repeating the work means building a new
coroutine from the same function — which is cheap, and is why producer functions are usually
kept around and turned into coroutines on demand rather than stored as coroutines.
</Gotcha>
