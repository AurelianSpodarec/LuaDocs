Searches nothing when you call it. What it returns is a *function* — an iterator that
finds the next match each time it is called — which is what a generic `for` loop wants, and
what turns "every match in this string" into a two-line loop.

<RunnableExample code={`local shopping_note = "2 apples, 3 pears, 12 plums"\nfor quantity, fruit_name in string.gmatch(shopping_note, "(%d+) (%a+)") do\n  print(fruit_name, quantity)\nend\n-- Expected output:\n-- apples\t2\n-- pears\t3\n-- plums\t12`} />

## Syntax

```lua
string.gmatch(s, pattern [, init])
```

<Parameters>
  <Param name="s">The string to walk.</Param>
  <Param name="pattern">The [pattern](/docs/standard-library/string/patterns) each turn looks for.</Param>
  <Param name="init">Where the *first* search begins; every later turn carries on from the previous match. Omitted, the walk starts at the first byte.</Param>
</Parameters>

<Returns>
  <Return type="function">An iterator. Each call advances to the next match and returns exactly what [`string.match()`](/docs/standard-library/string/match) would return for it. Once the matches run out it returns no values at all, which is what ends a generic `for`.</Return>
</Returns>

## Description

Every call resumes where the previous match ended, so the string is covered once, left to
right, and no two matches overlap. `"aa"` over `"aaa"` therefore produces one match and not
two: the second `a` has already been consumed by the first.

`init` moves where the first search begins and leaves the rest of the walk alone. It is a
position in `s`, counted from 1 or backwards from the end the way
[`string.sub()`](/docs/standard-library/string/sub) counts one, and a position landing
before the string begins the walk at the first byte. It may sit one byte past the end,
where an empty pattern still has a turn to take; further out than that, what comes back is
an iterator that yields nothing and a loop whose body never runs — not an error.

The iterator is an ordinary function and nothing obliges you to put it in a `for`. Storing
it in a name and calling it by hand is how a match is taken one at a time, out of step with
a loop — reading a header before the body, say, or pulling only as many matches as are
wanted.

## Examples

### Adding up every number in a line

<RunnableExample code={`local receipt_line = "coffee 3, pastry 2, juice 4"\nlocal item_total = 0\nfor quantity in string.gmatch(receipt_line, "%d+") do\n  item_total = item_total + tonumber(quantity)\nend\nprint(item_total)\n-- Expected output: 9`} />

The pattern captures nothing, so each turn produces the matched text itself, and
`tonumber()` is what makes it something that can be added.

### Calling the iterator by hand

<RunnableExample code={`local next_name = string.gmatch("Ada Lovelace Byron", "%a+")\nprint(next_name())\nprint(next_name())\nprint(next_name())\nprint(select("#", next_name()))\n-- Expected output:\n-- Ada\n-- Lovelace\n-- Byron\n-- 0`} />

The fourth call has nothing left to find and returns *no values*, which `select("#", ...)`
counts as zero. That is the signal a `for` loop reads as the end of the walk.

### Skipping a prefix that would otherwise match

<RunnableExample code={`local shipping_label = "ORDER-4471: 2 boxes, 5 crates, 1 pallet"\nlocal colon_position = string.find(shipping_label, ": ", 1, true)\nfor quantity in string.gmatch(shipping_label, "%d+", colon_position) do\n  print(quantity)\nend\n-- Expected output:\n-- 2\n-- 5\n-- 1`} />

Starting the walk at the colon keeps the digits of the order number out of it, without
having to cut the label into a new string first.

## Gotchas

<Gotcha title="A leading caret does not anchor the walk">
`string.gmatch()` is the one function that does not honour `^` as an anchor;
[Patterns](/docs/standard-library/string/patterns) records the exception and the reason for
it. What happens instead is the part that bites: the caret is not quietly dropped, it is
matched as an ordinary character. `"^%a+"` therefore looks for a caret followed by letters,
and walks over nothing at all in text that contains no caret — which reads at the call site
as a pattern that simply found no matches rather than as a pattern that cannot work here.
Where a match really has to be at the start,
[`string.match()`](/docs/standard-library/string/match) or
[`string.find()`](/docs/standard-library/string/find) is the function that anchors.
</Gotcha>

<Gotcha title="The iterator is spent, not reusable">
Reaching the end of the string leaves the iterator permanently exhausted; it does not
rewind. Keeping one in a table field or an upvalue and looping over it a second time runs
the body zero times and raises nothing, so the loop looks like a string that had no matches
in it rather than one already walked. Call `string.gmatch()` again for each pass — the call
is cheap, and it is the fresh iterator that is the point.
</Gotcha>
