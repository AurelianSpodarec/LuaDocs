title: string.dump()
description: Turn a Lua function into a binary chunk that can be loaded back.
lua-compat: string.dump
entry-type: function
source: https://www.lua.org/manual/5.5/manual.html#pdf-string.dump
---

Hands back the compiled form of a function — a *binary chunk* — as an ordinary Lua string.
Nothing in the library reads it: it is written for
[`load()`](/docs/standard-library/globals/load), which turns it back into a callable
function. It is the one `string` function that takes code rather than text, and the reason
to reach for it is to put a function somewhere a function cannot go — a file, a cache, a
message.

<Only since="5.2">

<RunnableExample code={`local function shipping_cost(weight_grams)\n  return 4.5 + weight_grams * 0.002\nend\n\nlocal compiled = string.dump(shipping_cost)\nlocal restored = load(compiled)\nprint(type(compiled))\nprint(restored(1500))\n-- Expected output:\n-- string\n-- 7.5`} />

</Only>

<Only before="5.2">

<RunnableExample code={`local function shipping_cost(weight_grams)\n  return 4.5 + weight_grams * 0.002\nend\n\nlocal compiled = string.dump(shipping_cost)\n-- loadstring(compiled) is what turns this string back into a function\nprint(type(compiled))\nprint(#compiled > 0)\n-- Expected output:\n-- string\n-- true`} />

</Only>

## Syntax

<Only before="5.3">

```lua
string.dump(function)
```

</Only>

<Only since="5.3">

```lua
string.dump(function [, strip])
```

</Only>

<Parameters>
  <Only before="5.2">
    <Param name="function">The Lua function to compile. It must be written in Lua rather than in C, and it must have closed over nothing.</Param>
  </Only>
  <Only since="5.2" before="5.3">
    <Param name="function">The Lua function to compile. It must be written in Lua rather than in C.</Param>
  </Only>
  <Only since="5.3">
    <Param name="function">The Lua function to compile. It must be written in Lua rather than in C.</Param>
    <Param name="strip">Anything other than `nil` or `false` asks for a chunk that may leave some debug information out, to save space. Omitted, everything is kept.</Param>
  </Only>
</Parameters>

<Returns>
  <Return type="string">A binary chunk holding the compiled function.</Return>
</Returns>

<Errors>

- Raises when the value given is not a function.
- Raises when the function was written in C rather than in Lua.

</Errors>

## Description

The result is a Lua string like any other — it can be measured, concatenated, kept in a
table or written to a file. It is not text: most of it is byte values with no printable
character behind them, and it begins with an escape byte, which is the one byte a loader
consults to tell a compiled chunk from source. The three that follow spell `Lua` and are
checked when the chunk is read rather than when it is recognised.

None of that hides anything. Every string constant the function used sits in the chunk
exactly as it was written, and the names of the function, its parameters and its locals
are there beside them.

<RunnableExample code={`local function greet_customer(name)\n  return "hello, " .. name\nend\n\nlocal compiled = string.dump(greet_customer)\nprint(string.byte(compiled, 1, 4))\nprint(string.find(compiled, "hello, ", 1, true) ~= nil)\n-- Expected output:\n-- 27\t76\t117\t97\n-- true`} />

<Only since="5.2">

Reading it back is [`load()`](/docs/standard-library/globals/load), which accepts source
text and binary chunks alike and decides between them by looking. Its `mode` argument
narrows that: `"t"` for text only, `"b"` for binary only, `"bt"` — the default — for
either. What comes back is a *copy* of the function, not the function itself; loading the
same chunk twice gives two independent functions.

A chunk records how many upvalues the function has and nothing about what they held. On
reload they come back fresh, and `load()` fills them: the first gets the environment —
the `env` argument if one was passed, otherwise the globals table — and the rest get
`nil`. So a closure over a counter, a cache or a configuration table comes back having
lost the value it closed over, and the original keeps its own copy untouched.

<RunnableExample code={`local order_count = 0\nlocal function record_order()\n  order_count = order_count + 1\n  return order_count\nend\n\nprint(record_order())\nlocal restored_recorder = load(string.dump(record_order))\nlocal upvalue_name, upvalue_value = debug.getupvalue(restored_recorder, 1)\nprint(upvalue_name, type(upvalue_value))\nprint(order_count)\n-- Expected output:\n-- 1\n-- order_count\ttable\n-- 1`} />

The copy still knows the upvalue is called `order_count`; what it holds is the globals
table that `load()` put there, because it happened to be first in the list. Carrying the
values across is a separate job, and
[`debug.getupvalue()`](/docs/standard-library/debug/getupvalue) and
[`debug.setupvalue()`](/docs/standard-library/debug/setupvalue) are what it is done with.

</Only>

<Only before="5.2">

Reading it back is [`loadstring()`](/docs/standard-library/globals/loadstring), which
accepts source text and binary chunks alike and decides between them by looking. What
comes back is a *copy* of the function, not the function itself; loading the same chunk
twice gives two independent functions.

A function this call compiles is one that closed over nothing. A counter, a cache or a
configuration table captured from an enclosing block puts the function outside what this
call covers, and nothing dependable comes of dumping one; turning the captured value into
a parameter is what brings the function back within reach.

</Only>

<Only since="5.3">

`strip` asks for a smaller chunk in exchange for debug information. Exactly how much goes
is not promised — only that some of it *may* be left out — so what survives is an
implementation matter rather than a contract. What goes first is the material that names
things: the chunk's source name, and the names of parameters and locals. The string
constants stay, because the function needs them to run, and a stripped function runs
identically.

<RunnableExample code={`local function label_total(unit_price, quantity)\n  return "total: " .. unit_price * quantity\nend\n\nlocal full_chunk = string.dump(label_total)\nlocal stripped_chunk = string.dump(label_total, true)\nprint(#stripped_chunk < #full_chunk)\nprint(load(stripped_chunk)(2.5, 4))\nprint(string.find(stripped_chunk, "total: ", 1, true) ~= nil)\nprint(debug.getinfo(load(stripped_chunk), "S").short_src)\nprint(debug.getlocal(load(full_chunk), 1))\n-- Expected output:\n-- true\n-- total: 10.0\n-- true\n-- ?\n-- unit_price`} />

Every one of those names is stored in the chunk as a string, so how much is saved depends
on how many the function carried. The cost is paid later, and by somebody else: a
traceback through a stripped function has no source name to print and cannot say where in
the function it was, so the frame reads `?`, and an error raised inside one arrives with
no position on it at all. Strip a chunk you are shipping; keep a whole one for anything
you expect to debug.

</Only>

<Warning>
A binary chunk belongs to the Lua that produced it. Nothing holds the layout of a compiled
chunk still from one Lua version to the next, so a chunk written today is readable only by
the version that wrote it. Keep the source alongside anything you cache.

Loading one is a separate hazard. Lua does not check that a binary chunk is internally
consistent, and a crafted one can crash the interpreter — unlike source text, which can
only ever fail to compile.

<Only since="5.2">

`load()` accepts binary chunks by default, so code that loads input from a file, a socket
or a user must pass `"t"` to refuse them.

</Only>
</Warning>

## Examples

<Only since="5.2">

### Compiling once and loading twice

<RunnableExample code={`local function apply_discount(price_pennies, discount_pennies)\n  return price_pennies - discount_pennies\nend\n\nlocal cached_chunk = string.dump(apply_discount)\nlocal first_copy = load(cached_chunk)\nlocal second_copy = load(cached_chunk)\nprint(first_copy(20000, 2000))\nprint(second_copy(20000, 5000))\nprint(first_copy == second_copy)\n-- Expected output:\n-- 18000\n-- 15000\n-- false`} />

Compiling is done once and the chunk is reused, which is the whole reason to keep one. The
two copies behave the same and are separate values, so giving one away does not hand over
the other.

### Refusing a binary chunk that arrived from elsewhere

<RunnableExample code={`local function format_receipt(total)\n  return "total: " .. total\nend\n\nlocal incoming_chunk = string.dump(format_receipt)\nlocal text_only, refusal = load(incoming_chunk, "receipt", "t")\nprint(text_only)\nprint(refusal)\nprint(load(incoming_chunk, "receipt", "b")(12.5))\n-- Expected output:\n-- nil\n-- attempt to load a binary chunk (mode is 't')\n-- total: 12.5`} />

The `mode` argument is the switch: `"t"` declines the chunk without running any of it,
`"b"` insists on one. Deciding which of the two you are loading, rather than letting the
loader decide, is the difference between running code you compiled and running bytes
somebody sent you.

</Only>

<Only before="5.2">

### Keeping a compiled function in a file

<RunnableExample code={`local cache_path = "string-dump-example-cache.luac"\n\nlocal function apply_discount(price_pennies, discount_pennies)\n  return price_pennies - discount_pennies\nend\n\nlocal writing = assert(io.open(cache_path, "wb"))\nwriting:write(string.dump(apply_discount))\nwriting:close()\n\nlocal reading = assert(io.open(cache_path, "rb"))\nlocal cached_chunk = reading:read("*a")\nreading:close()\n-- loadstring(cached_chunk) turns these bytes back into the function\nprint(#cached_chunk > 0)\nprint(cached_chunk:byte(1))\n\nos.remove(cache_path)\n-- Expected output:\n-- true\n-- 27`} />

Compiling is done once and the bytes are kept, which is the whole reason to make a chunk:
a function is put somewhere a function cannot go, and comes back without being compiled
again. The file is opened in binary mode both ways, because a chunk is bytes rather than
text and a translated line ending would ruin it.

</Only>

## Gotchas

<Gotcha title="Only a function written in Lua can be dumped">
There is no compiled form to hand back for a function implemented in C — every function
the standard library provides, and every function a host program installs. The call raises
rather than returning `nil`, so a program that dumps whatever it is given needs
[`pcall()`](/docs/standard-library/globals/pcall) around it.

<RunnableExample code={`local dump_succeeded, dump_error = pcall(string.dump, string.format)\nprint(dump_succeeded)\nprint(dump_error)\n-- Expected output:\n-- false\n-- unable to dump given function`} />
</Gotcha>

<Only since="5.3">

<Gotcha title="Anything but nil and false strips">
`strip` is read as a truth value, not as a flag that has to be `true`, and in Lua only
`nil` and `false` are false. `0` and `""` therefore both strip, which is the opposite of
what someone writing `string.dump(handler, 0)` from a C habit intends.

<RunnableExample code={`local function label_order(order_id)\n  return "order " .. order_id\nend\n\nprint(#string.dump(label_order, 0) < #string.dump(label_order, false))\nprint(#string.dump(label_order, nil) == #string.dump(label_order))\n-- Expected output:\n-- true\n-- true`} />
</Gotcha>

</Only>
